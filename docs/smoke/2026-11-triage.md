# Smoke corpus: compile-break and wiring suspects by cause, November 2026

The rules that claim code would not compile or an application would not start (`hard_rules` in
[scripts/corpus.sh](../../scripts/corpus.sh)) must never fire on code that builds. This report takes every
finding of theirs on the smoke corpus ([corpus/smoke.tsv](../../corpus/smoke.tsv): 154 open-source projects
the rules were never tuned on) and groups the findings by **cause**. For each cause it gives a reproducer of a
few lines, the place in grounds that goes wrong, and a fix in the spirit of "unknown means silent". **It
changes no rule and no line of Rust.** The data is in [2026-11-suspects.tsv](2026-11-suspects.tsv): one line
per finding with project, path, line, rule, cause, verdict, and who read it.

## Totals

- **Before:** 12,339 findings in 74 projects. That count is from the run in #65, made before #61 and #62.
- **Now:** **7,914 findings in 67 projects**: grounds 0.0.12, master at `acb4c3a`, run as
  `python3 -I scripts/smoke.py --keep` over all of `corpus/smoke.tsv`, in two shards.
  - **7,198 false** in 63 projects.
  - **715 true** in 15 projects. Most of them are in files no build compiles (cause
    [not-built](#not-built)); 19 are Spring tutorials that fail on purpose.
  - **1 unclear.**
- **Crashes:** none. No panic, no timeout, no abnormal exit, and every project printed valid JSON. `smoke.py`
  reported 0 failures and 0 fetch failures.
- **Parse errors:** 3,101 in 996 files, as `smoke.py` reports them. Most are jdt-core's test inputs (623 files),
  then lombok 94, manifold 65 and quarkus 62. Parse errors were not triaged.
- **Projects that no longer appear:** jdt-core (hinted at about 5,200 before) and j2cl have no
  hard-rule finding now. Both carry many copies of JDK classes (jdt-core's `JCL/*`, j2cl's `jre/`). #62's guard on classes
  declared twice is the likely reason; this was not checked. jenkins has 33, not the ~1,450 SequencedCollection findings hinted at (most of those are gocd's).
  bazel's "`Object` has no method `getClass`" is confirmed
  ([jdk-class-in-sources](#jdk-class-in-sources)), and so are spring-batch's 138 bean-name-conflict findings
  ([independent-contexts-merged](#independent-contexts-merged)).
- **Causes:** 38, plus 1 finding not assigned. 108 findings were read by hand at the code and 268 by
  review passes (see [Checked by hand](#checked-by-hand)). The rest were assigned by a counterfactual rerun
  or by a message pattern, each pattern confirmed by reading and by a reproducer.

## The five causes that would remove the most false reports

1. **[A source file declares a JDK class and replaces the JDK's own](#jdk-class-in-sources)**: 2,341 false reports in 4 projects.
2. **[Java release detected lower than the code's](#release-too-low)**: 1,922 false reports in 13 projects.
3. **[A class declared twice: the "certain copy" is the wrong one](#wrong-duplicate-copy)**: 1,120 false reports in 2 projects.
4. **[Annotated receiver parameter read as an ordinary parameter](#receiver-parameter)**: 638 false reports in 3 projects.
5. **[Manifold language extension](#manifold)**: 239 false reports in 1 project.

Together they account for 6,260 of the 7,198 false reports. The fixes for the first four are local: one function each.

## How the findings were assigned

1. **Counterfactual reruns.** Where a cause can be switched off from the outside, each affected project was
   checked again with the same binary and only that one change, using `--rules` set to the hard rules. A
   finding that disappears is assigned to the cause. The reruns:
   - `java_release = 21` in `grounds.toml`, on every project with findings
     ([release-too-low](#release-too-low));
   - the files that declare JDK classes, excluded with `exclude = [...]` on bazel, netty, libgdx and lombok
     ([jdk-class-in-sources](#jdk-class-in-sources));
   - the GWT super-source copy, excluded on guava, and the test-data source trees on javaparser
     ([wrong-duplicate-copy](#wrong-duplicate-copy));
   - annotated receiver parameters, stripped from calcite, androidx-media and checker-framework with a regex,
     then restored with `git checkout` ([receiver-parameter](#receiver-parameter)).

   A rerun can also add findings (sonar-java targets Java 25; with 21, the JDK is "complete" and thousands of
   new reports appear). Only disappearances count.
2. **Message and path patterns.** Most of the remaining findings were assigned by project and message
   pattern, each pattern confirmed by reading the code at several findings and by a reproducer. Two
   refinements:
   - [default-package-across-dirs](#default-package-across-dirs) also requires that the name is declared in
     the default package of *another* directory;
   - a finding in a `@skip-test` file that never imports the name it uses goes to
     [not-built](#not-built), because those files really do not compile.
3. **The long tail.** 268 findings in 42 projects were left after steps 1 and 2. Each was read at the code by
   one of three review passes, run in parallel with the list of causes as their only context. Each pass wrote
   a reproducer for each new cause. I re-ran all of their reproducers and re-read a few of their verdicts
   against the code (wildfly's JAX-RS `@Produces`, jetty's anonymous `Rule`, cassandra's inherited
   `liveAndDown`, the tracked-but-ignored files in eugenp, the `com.baeldung` application that scans two
   `Cat` components).

Every reproducer below was run with the same binary; the output shown is what it printed. The reproducers are
independent of each other and of the corpus: a fresh directory, no `grounds.toml`, no jars. Where an
annotation must stay unresolved, as it is on the corpus, its stubs were kept out of the analysed directory.

## Causes

<a id="jdk-class-in-sources"></a>
### 1. A source file declares a JDK class and replaces the JDK's own

`jdk-class-in-sources`: **2,341 findings** in 4 projects (bazel 1,435, lombok 732, netty 110, libgdx 64). Verdict: **false**.

**Where:** `Index::class` (crates/grounds-index/src/index.rs:477): a project class always wins over the classpath, the JDK included.

A project that carries a stand-in for a JDK class makes that stand-in *the* class for the whole
project. bazel has `third_party/ijar/test/Object.java`, an empty `package java.lang; class Object {}` used as
test data for ijar: every `getClass()`, `equals()`, `hashCode()` and `toString()` on anything is then
"missing" (1,435 findings). The other three:

- lombok keeps compile-only stubs of javac internals (`src/stubsstubs/com/sun/tools/javac/...`) that its real
  build replaces with the JDK's `jdk.compiler` (732);
- netty has `varhandle-stub`, `ffm-stub` and `transport-sctp/src/main/java/com/sun/nio/sctp` stand-ins
  (`MethodHandle`, `Module`, `Association`) that exist so the code compiles on old JDKs (110);
- libgdx has GWT emulation of `java.lang.Thread`, `java.nio.Buffer` and others (64).

No build compiles these files together with the code that uses the real class: javac would refuse a source
`java.lang.Object` in the unnamed module, and the stubs are compile-only or GWT-only.

Evidence: excluding the stand-in directories with `exclude = [...]` removes every one of these findings:
bazel 1,441 to 6, lombok 761 to 29, netty 125 to 30, libgdx 64 to 19 (the 19 left are new findings, not
these). netty's 7 findings on its `com.sun.nio.sctp` stand-ins were not part of that exclusion; they were
assigned by reading.

**Examples:**

- [bazel `DepsCheckerClassVisitor.java:251`](https://github.com/bazelbuild/bazel/blob/99eb9c52162d6e59f6c6d08444bdf04b9b14d57e/src/java_tools/import_deps_checker/java/com/google/devtools/build/importdeps/DepsCheckerClassVisitor.java#L251): `Object` has no method `getClass`
- [lombok `CompilerMessageSuppressor.java:245`](https://github.com/projectlombok/lombok/blob/effbae9382a9c5e93d141446287af82d50cda53f/src/core/lombok/javac/CompilerMessageSuppressor.java#L245): `JCDiagnostic` has no method `getStartPosition`
- [netty `ConcurrentSkipListIntObjMultimap.java:1603`](https://github.com/netty/netty/blob/bc6f58a174e159328dc6fb6d07d7f701e7ec9013/common/src/main/java/io/netty/util/concurrent/ConcurrentSkipListIntObjMultimap.java#L1603): `MethodHandle` has no method `invokeExact`

**Reproducer** (a fresh directory; no `grounds.toml`, no jars):

`src/main/java/app/Visitor.java`

```java
package app;

class Visitor {
    String name(Object value) { return value.getClass().getName(); }
}
```

`third_party/ijar/test/Object.java`

```java
package java.lang;

class Object {
}
```

`grounds check --root .` reports:

```
src/main/java/app/Visitor.java:4:46: error [unresolved-method] `Object` has no method `getClass`
```

**Fix:** When a source file declares a class in a package the JDK owns (`java.*`, `javax.*` packages exported by
JDK modules, `jdk.*`, `com.sun.*` of the runtime image), keep the JDK's class for every other file, and treat
the name as declared twice (`copy_is_certain` false) so that nothing about it is claimed.

**Cost in missed true findings:** None measured: no true finding on the corpus depends on a project's own `java.*` class. A project that
really patches a JDK module (`--patch-module`) would lose reports about calls into its patched class.

<a id="release-too-low"></a>
### 2. Java release detected lower than the code's

`release-too-low`: **1,922 findings** in 13 projects (gocd 1,376, graal 317, hibernate-orm 63, checker-framework 35, jenkins 33, lucene 33, trino 31, guava 15, dbeaver 7, jextract 6, mapstruct 4, junit5 1, kafka 1). Verdict: **false**.

**Where:** `java_release::infer` (crates/grounds-engine/src/java_release.rs:24), used by `Config::java_release`.

One JDK symbol table serves the whole project. Its release is the highest one that some build file states
as a literal. Any JDK class or member newer than that is "missing": `unresolved-method` fires on Java 21
`SequencedCollection.getFirst()`/`getLast()` called on project collections, and `missing-jdk-import` on
`java.io.Serial`, `java.util.HexFormat`, `java.lang.classfile` and `java.lang.foreign`. On this corpus the
release was read too low in five ways:

1. The real release is an expression grounds does not read, and a side module's literal wins.
   - gocd: the root sets `options.release.set(goVersions.targetJavaVersion as Integer)` (21) and two
     plugin-API modules say `options.release.set(11)`. Detected 11; 1,376 findings.
   - hibernate-orm: the release comes from `orm.jdk.base=17` in `gradle.properties` through `jdkVersions.*`
     variables, while the build-logic project `local-build-plugins/build.gradle` says `sourceCompatibility = 11`.
     Detected 11; 63 findings.
2. The real release is outside the repository. jenkins inherits it from the `org.jenkins-ci:jenkins` parent
   POM. The only literal in the tree is `war/pom.xml`'s `<release>11</release>` for a launcher class; 33 findings.
3. A property or version catalog grounds does not know, so nothing is found and the default 21 is used.
   trino sets `project.build.targetJdk` = 25 (airbase); lucene has `minJava = "25"` in
   `gradle/libs.versions.toml`.
4. `<source>`/`<target>` without `--release`. guava and mapstruct set 1.8. javac then compiles against the
   full API of the JDK it runs on (guava builds with a newer toolchain), so the Java 9+ classes and the Java 19
   `ExecutorService.close()` they use are legal.
5. Code that needs a release above the installed JDK 21:
   - graal (25), netty's `CleanerJava24Linker`, checker-framework's `jtreg/nullness/jdk25`, jextract samples;
   - with the right release grounds warns that the JDK is older and stays silent;
   - with 17 or 21 detected, it reports the newer classes as missing.

Evidence: re-running with `java_release = 21` in `grounds.toml` removes 1,805 distinct findings (gocd
1,393 to 17; the 17 left are cause *spring-xml-beans*). The Java 22–25 imports of graal, trino, lucene,
netty, jextract and checker-framework were assigned by message and checked against each project's build.

**Examples:**

- [gocd `JobInstancesRepresenter.java:39`](https://github.com/gocd/gocd/blob/96f58726b28a72cf389507c34128d76c2392c166/api/api-job-instance-v1/src/main/java/com/thoughtworks/go/apiv1/jobinstance/representers/JobInstancesRepresenter.java#L39): `JobInstances` has no method `getFirst`
- [graal `CustomizedBytecodePattern.java:27`](https://github.com/oracle/graal/blob/e08189307e365a9ecd1cc4debda79e97730dc94d/compiler/src/jdk.graal.compiler.test/src/jdk/graal/compiler/core/test/CustomizedBytecodePattern.java#L27): `java.lang.classfile.ClassFile` is not public API in Java 17
- [hibernate-orm `SybDriverPatcher.java:5`](https://github.com/hibernate/hibernate-orm/blob/1c23837a41a0f00186920356897d974357290d04/ci/SybDriverPatcher.java#L5): package `java.lang.classfile` is not public API in Java 11

**Reproducer** (a fresh directory; no `grounds.toml`, no jars):

`build.gradle`

```groovy
ext.targetJavaVersion = 21
subprojects {
  apply plugin: 'java'
  tasks.withType(JavaCompile).configureEach {
    options.release.set(targetJavaVersion as Integer)
  }
}
```

`settings.gradle`

```groovy
include 'app', 'plugin-api'
```

`app/src/main/java/app/Stages.java`

```java
package app;

import java.util.ArrayList;

public class Stages extends ArrayList<String> {
    String first() { return getFirst(); }
}
```

`plugin-api/build.gradle`

```groovy
compileJava {
  options.release.set(11)
}
```

`plugin-api/src/main/java/api/Plugin.java`

```java
package api;

public interface Plugin { }
```

`grounds check --root .` reports:

```
app/src/main/java/app/Stages.java:6:29: error [unresolved-method] Method `getFirst` is not defined in `Stages` or its enclosing classes
```

**Fix:** Make the release *unknown* rather than low:
- when any build file sets the release with something `infer` cannot evaluate (a variable, a property it
  cannot resolve, a parent POM outside the tree, a toolchain from a catalog), or a module sets only
  `source`/`target`;
- then treat JDK members as possibly newer than the release, as for `JdkApi::Newer`: hierarchies through
  JDK classes are incomplete for "missing member" claims, and `missing-jdk-import` does not run;
- report a JDK API as too new only when the file's own module states its release as a literal `release`.

Lower-priority alternative: when inference is uncertain, take the installed JDK's release instead of the
inferred one.

**Cost in missed true findings:** Calls to a JDK method newer than the target, in projects whose release cannot be read, go unreported.
None of the 1,922 findings of this cause is true.

<a id="wrong-duplicate-copy"></a>
### 3. A class declared twice: the "certain copy" is the wrong one

`wrong-duplicate-copy`: **1,120 findings** in 2 projects (guava 710, javaparser 410). Verdict: **false**.

**Where:** `Index::certain_copy` and `module_dir` (crates/grounds-index/src/index.rs:438 and :1099).

#62 made grounds silent about a class declared in several files unless it can tell which copy a file
compiles against. The test for "certain" is the copy in the file's own module and source set, and the module
is the path before `/src/`. Two layouts break it.

- **guava (710).**
  - `LocalCache`, `MapMaker` and the other cache classes exist three times: `guava/src`, `android/guava/src`,
    and the GWT super-source copy `guava-gwt/src-super/.../super/...`.
  - The tests in `guava-tests/test/...` and `android/guava-tests/...` have no `/src/` in their path, nor does
    the GWT copy. All of them get module `""`.
  - So the GWT copy, which lacks the package-private fields the tests use (`segments`, `maxWeight`), counts as
    "the copy of their module".
- **javaparser (410).**
  - `javaparser-symbol-solver-testing/src/test/test_sourcecode/` holds old copies of javaparser's own
    sources as test data.
  - `source_set_of` calls them source set `test`, the same as the real tests in `src/test/java`. They then
    win over `javaparser-core/src/main/java`.
  - The test-data files themselves get the same treatment the other way round: they are resolved against
    today's core classes, which have different signatures.

Evidence: with `exclude = ["guava-gwt/**"]` guava drops from 726 findings to 16; with the test-data trees
excluded, javaparser drops from 410 to 0.

**Examples:**

- [guava `ChainBenchmark.java:47`](https://github.com/google/guava/blob/a6a94cc78bb63ffea9c2a0cd74ee0997720053f2/android/guava-tests/benchmark/com/google/common/cache/ChainBenchmark.java#L47): `LocalCache` has no field `segments`
- [javaparser `JavaConceptsInnerClasses.java:35`](https://github.com/javaparser/javaparser/blob/2579466f4421bd0c722c8539831bafbb0d90c583/javaparser-core-testing/src/test/test_sourcecode/com/github/javaparser/printer/JavaConceptsInnerClasses.java#L35): `JavaConceptsInnerClasses` has no field `arr`
- [guava `ChainBenchmark.java:53`](https://github.com/google/guava/blob/a6a94cc78bb63ffea9c2a0cd74ee0997720053f2/android/guava-tests/benchmark/com/google/common/cache/ChainBenchmark.java#L53): `LocalCache` has no method `hash`; did you mean `hashCode`?
