# Hold-out precision and recall, November 2026 (third set)

grounds 0.0.12 (release build of master at `e76fba0`, after #74, #76, #78,
#80 and #84), run on 20 open-source Java projects that are in none of
[corpus/projects.tsv](../../corpus/projects.tsv),
[corpus/smoke.tsv](../../corpus/smoke.tsv) and the first two sets of
[corpus/holdout.tsv](../../corpus/holdout.tsv). Both earlier sets were used
to fix rules, so they can no longer measure anything. This third set measures
current master the way the [first](2026-11.md) and [second](2026-11b.md)
reports did in check mode, the way the [replay](2026-11-replay.md) did in
change mode, and the way the [recall report](2026-11-recall.md) did for
recall, so the numbers can be put side by side. **It measures only.** No
rule, fixture or line of Rust was changed because of it, and nothing from
these projects was made into a fixture or a test.

The question it answers: **what may the README claim for 0.1.0?** The promise
is narrow: in change mode (`grounds changed --base <commit>`), a report of
the six `stable in changed` rules is right. A rule is promoted on precision
measured on projects it was never tuned on, with a working bar of **at least
20 judged findings with at most 1 false**.

Every verdict is in [2026-11c.tsv](2026-11c.tsv): rule, project, path, line,
verdict and reason (a reason for every verdict, true ones included), then
`mode` (`check` for `grounds check`, `changed` for the replay) and the commit.

## The false report of a stable rule

### `unresolved-constructor`: a record with a varargs component and a compact constructor (4 false, jnosql)

[jnosql `Function.java`](https://github.com/eclipse-jnosql/jnosql/blob/fa763512aee80f210d24bb68df47006a7e88a479/jnosql-mapping/jnosql-mapping-semistructured/src/main/java/org/eclipse/jnosql/mapping/semistructured/Function.java#L109)
lines 109, 121, 133 and 145:

```java
record DefaultFunction(String name, String field, Object... arguments) implements Function {
    DefaultFunction {                       // compact canonical constructor
        Objects.requireNonNull(name, "name is required");
        ...
    }
}
...
return new DefaultFunction("UPPER", field);  // grounds: No constructor of `DefaultFunction`
                                             // takes 2 argument(s); available:
                                             // DefaultFunction(String, String, Object[])
```

The canonical constructor of a record whose last component is `T...` is a
varargs constructor (JLS 8.10.4), whether it is implicit or declared in
compact form, so the call passes zero varargs and compiles. The project
builds; the same code compiles with javac 21.

**Reproducer** (synthetic, two files, javac accepts both):

```java
// p/R.java
package p;
record R(String name, String field, Object... arguments) {
    R { arguments = arguments.clone(); }
}
// p/Use.java
package p;
class Use { Object a() { return new R("UPPER", "f"); } }
```

`grounds check` reports `unresolved-constructor` on `Use.java:2`. Without the
compact constructor (`record R(String name, String field, Object... arguments) {}`)
it reports nothing. In change mode, on a git repository whose base has `R`
and a commit that adds `a()`, `grounds changed --base HEAD~1 --no-daemon`
reports `unresolved-constructor ... maturity: stable` on the new line: a
false report of the promise. No replayed commit added such a call, which
says the shape is rare in those 465 commits, not how rare it is.

**Where:** `crates/grounds-index/src/stubs.rs`, the `constructor_declaration
| compact_constructor_declaration` arm (about line 1185). For a compact
constructor it builds the parameters from the record components and returns
`(ps, false)`: the varargs flag is always false. The implicit canonical
constructor (about line 1287) does look at whether the record header's last
parameter is a `spread_parameter`, which is why the record without a compact
constructor is fine.

**Proposed fix:** set the flag for a compact constructor the same way as for
the implicit one, from the record header (`node.field("parameters")`, last
child of kind `spread_parameter`), and add the reproducer above as a
fixture of `unresolved-constructor` (expect nothing), with a second call
that really has too few arguments (`new R("a")`, expect a report) so that
the fix does not make the rule silent on records.

No other false report of a stable rule was found, in either mode.

**Fixed on master since.** While this ran, #85 ("A record's compact
constructor is varargs when its last component is") was merged, at
`bdd011b`; it was made independently of this report. A release build of
`bdd011b` reports nothing on the reproducer above, in `grounds check` or on
the synthetic commit with `grounds changed --base`, and no compile-break
finding on jnosql at the pinned commit. Every number in this report is
still that of `e76fba0`, which is what was measured: the fix makes this set
spent for `unresolved-constructor`, as the earlier sets are, so a
rule that was 2 true of 6 here cannot be re-measured on it.

## Change mode: the replay

Each project's main line was fetched (`--depth 151` from the pinned commit),
`[classpath] scan_caches = false` added as `grounds.toml`, and replayed with

    python3 -I scripts/replay.py DIR --grounds target/release/grounds --commits 25 --budget 1500 --out P.json

which asks `grounds changed --base <parent>` at each of the last 25 commits
with Java changes, through the daemon (which follows the whole walk) and
with `--no-daemon`, compares the two answers field for field, then deletes
and restores every Java file and renames a much-called method, asking both
ways each time. The budget cut fineract to 21 commits, hertzbeat to 15 and
graylog to 13 (a step there takes 55–90 s); spring-boot-admin had only 16
commits with Java changes in the 151 fetched. Then every warning and error
on the changed lines and every place reported broken was collected for the
same commits with `scripts/replay_findings.py --from` (fresh runs).
`replay_findings.py --from` no longer accepts a current replay.py report as
it is: replay.py now also writes the `deleted`, `restored` and `renamed`
steps, which are not commits, and `replay_findings.py` stops at
`git rev-parse deleted^`. It was given a copy of each report with only the
commit steps. (That script is outside what this task may change; the fix is
to skip steps whose `commit` is not a commit.)

### The 12 break reports

Both logback commits did not compile, and the next commit fixed each. Each
was checked with javac 21 on the sources exported at the commit and at its
parent (`git archive`, `module-info.java` left out because no dependency
jars were there), without dependency jars:

- [`853ecd4`](https://github.com/qos-ch/logback/commit/853ecd46c3ea1c767d783eef46f48e605a09a735)
  "added a OptionHelper#toLopsidedBooleanObject" removes
  `ConfigurationModelHandler.scanStringToBoolean` and leaves
  `ConfigurationModelHandlerTest` calling it 11 times. grounds lists the 11
  calls as broken places; javac reports `cannot find symbol` on exactly
  those 11 lines at the commit and none at its parent. Commit `9df9673`, 25
  minutes later, fixes the test. **11 true** (`unresolved-method`).
- [`6bd64c2`](https://github.com/qos-ch/logback/commit/6bd64c2100e4b7c4a1ded870072f743fcfeff4b6)
  adds to `SizeAndTimeBasedArchiveRemover` an `@Override` of
  `getUncompressedFilesInPeriod`, a constructor calling a three-argument
  `super(...)` and reads of `fileNamePatternWithoutCompSuffix`, none of which
  `TimeBasedArchiveRemover` has yet. grounds reports the override; javac
  reports it too (`method does not override or implement a method from a
  supertype`) and the parent compiles cleanly. **1 true**
  (`override-matches-nothing`). javac also reports the `super(...)` call and
  the three field reads, which grounds did not report: four breaks missed on
  that commit (a recall observation; why was not looked into).

## How the third set was chosen

Written and committed (commit `701a27b`) before any finding was looked at; unchanged since.

The first two sets are spent: pull requests #70, #74, #76, #78, #80 and #84
fixed causes found on them. A third set of 20 projects measures current
master the same way. The rules for choosing it:

- **Fresh.** No project is in corpus/projects.tsv, corpus/smoke.tsv or either
  earlier set of corpus/holdout.tsv, and none is a fork (GitHub's `fork` flag
  was checked for every one) or a copy of one.
- **The same mix as before**: Maven and Gradle builds; from about 10,000 to
  several hundred thousand lines; Spring Boot applications and libraries,
  plain Spring, Micronaut, Quarkus, Jakarta EE/CDI, Guice and plain

- **Alive**: pushed to in 2026 where possible, pinned to the head of the
  default branch on 2026-11-11.
- Chosen from what the author knew of the Java ecosystem, before any of them
  was run. No project was dropped or added after a run.

**Supported.** In change mode, the stable rules have now been run after 979
real commits of 60 projects they were never tuned on (514 on the first two

commits that really did not compile, and all 12 were right (javac agrees).

all 1,531 scripted edits. After 1,184 scripted edits that certainly break
