# Hold-out precision, November 2026 (fourth set)

grounds at master `98f4a80` (0.1.0 and the install script; release build),
run on 40 open-source Java projects that are in none of
[corpus/projects.tsv](../../corpus/projects.tsv),
[corpus/smoke.tsv](../../corpus/smoke.tsv) and the first three sets of
[corpus/holdout.tsv](../../corpus/holdout.tsv). **It measures only.** No
rule, fixture or line of Rust was changed because of it, and nothing from
these projects was made into a fixture or a test.

The question it answers: **can `narrowing-compound-assignment`,
`log-placeholder-mismatch` and `assertj-assertion-without-check` be promoted
to stable in the next release?** The third report ([2026-11c](2026-11c.md))
found them right every time they were judged, but with too few findings to
judge. The bar is unchanged: **at least 20 judged findings, at most 1 false**,
on projects the rule was never tuned on. The set was chosen to give these
three rules findings, and the choice was committed (`84592f6`) before
grounds was run on it (below, "How the fourth set was chosen").

Every verdict is in [2026-11d.tsv](2026-11d.tsv): rule, project, path, line,
verdict and reason, true verdicts included.

## Every false report of a target rule

All seven are `narrowing-compound-assignment`. The rule
(`crates/grounds-rules/src/rules/numbers.rs`, `NarrowingCompoundAssignment`,
`check_node` at line 680) reports `x op= e` whenever the left side is an
integral type and `e` is `long` or floating-point, or the left is `float` and
`e` a non-constant `double`. It looks only at the types, never at what
values `e` can take, and its `sources` (line 673) name Error Prone and Sonar
only.

How a narrowing was judged, as in the earlier reports: **true** when the
implicit conversion can lose a value (overflow, or a dropped fraction), even
if that is harmless in practice. That is why `int checkTime *= 1.5` in a test
and `result += 31 * skip` in a `hashCode` are true. **False** when no value can
be lost, or when the author suppressed the warning. The blind second judge
(below) was given this definition and agreed with all seven.

### 1. A one-bit `long` result (5 findings, RoaringBitmap)

- [BitmapContainer.java:226](https://github.com/RoaringBitmap/RoaringBitmap/blob/5f1d0764ffaedababbe59729ba71c276c7d6177e/roaringbitmap/src/main/java/org/roaringbitmap/BitmapContainer.java#L226)
  `answer.cardinality -= (w ^ aft) >>> v;`
- [BitmapContainer.java:1216](https://github.com/RoaringBitmap/RoaringBitmap/blob/5f1d0764ffaedababbe59729ba71c276c7d6177e/roaringbitmap/src/main/java/org/roaringbitmap/BitmapContainer.java#L1216)
  `cardinality -= (aft - bef) >>> 63;`
- [MappeableBitmapContainer.java:276](https://github.com/RoaringBitmap/RoaringBitmap/blob/5f1d0764ffaedababbe59729ba71c276c7d6177e/roaringbitmap/src/main/java/org/roaringbitmap/buffer/MappeableBitmapContainer.java#L276),
  [:286](https://github.com/RoaringBitmap/RoaringBitmap/blob/5f1d0764ffaedababbe59729ba71c276c7d6177e/roaringbitmap/src/main/java/org/roaringbitmap/buffer/MappeableBitmapContainer.java#L286),
  [:1652](https://github.com/RoaringBitmap/RoaringBitmap/blob/5f1d0764ffaedababbe59729ba71c276c7d6177e/roaringbitmap/src/main/java/org/roaringbitmap/buffer/MappeableBitmapContainer.java#L1652):
  the same two shapes.

**Cause.** `aft` is `w` with bit `v` cleared, so `w ^ aft` has at most bit `v`
set, and shifting it right by `v` gives 0 or 1. `(aft - bef) >>> 63` is the
sign bit, 0 or 1. The library updates the cardinality without a branch, on
purpose. An `int` holds 0 and 1, so nothing can be lost.

**Reproducer** (synthetic; javac 21 compiles it, and the run checks a
million random inputs):

```java
public class B {
    int cardinality;
    void remove(long[] bitmap, char v) {
        long w = bitmap[v >>> 6];
        long aft = w & ~(1L << v);
        bitmap[v >>> 6] = aft;
        cardinality -= (w ^ aft) >>> v;      // grounds: `-=` silently narrows a `long` result to `int`
    }
    void clear(long[] bitmap, int index, long mask) {
        long bef = bitmap[index];
        long aft = bef & ~mask;
        cardinality -= (aft - bef) >>> 63;   // grounds: the same
        bitmap[index] = aft;
    }
}
```

A `main` drawing 1,000,000 random `w`, `v`, `bef` and `mask` found every
result in {0, 1}, and both values occurred. `grounds check` reports both
lines.

**Proposed fix.** Before reporting, bound the right-hand side by its bits:
`e >>> c` with a constant `c` has at most `64 - c` significant bits, and
`e & m` with a constant `m` at most the bits of `m`. If that fits the left
side's type (31 bits for `int`, as `-=` and `+=` may produce a negative), do
not report. That covers the two `>>> 63` findings. The three `(w ^ aft) >>> v`
findings have a variable shift, and proving them needs the fact that
`w ^ aft` has one bit, which the rule does not have. Either the rule stays
silent on any `>>>` by a non-constant amount on the right (the
bit-extraction idiom; it loses `i += x >>> n` with a variable `n`), or these
stay false and are counted. Fixture: both methods above, expect nothing, and
`int i; long x; i += x >>> 3;` still reported.

### 2. `InputStream.skip(n)` returns at most `n` (1 finding, aircompressor)

[SnappyInternalUtils.java:135](https://github.com/airlift/aircompressor/blob/acbd68293d625c34ae88fab6100783ec65b59225/src/main/java/io/airlift/compress/v3/snappy/SnappyInternalUtils.java#L135)
`toSkip -= source.skip(toSkip);` with `int toSkip`.

**Cause.** `skip(long n)` is specified to return the number of bytes
actually skipped, never more than `n`, and `n` here is the `int` itself. The
result fits in `int`.

**Reproducer** (synthetic; javac compiles it and it runs; `grounds check`
reports line 7):

```java
import java.io.*;
public class K {
    static int skipFully(InputStream in, int toSkip) throws IOException {
        while (toSkip > 0) {
            if (in.read() == -1) break;
            --toSkip;
            toSkip -= in.skip(toSkip);   // grounds: `-=` silently narrows a `long` result to `int`
        }
        return toSkip;
    }
}
```

**Proposed fix.** In the same `check_node`, do not report when the right side
is a call that resolves to `java.io.InputStream.skip`/`java.io.Reader.skip`
(or an override) whose argument is the left-hand variable itself. Narrow and
contract-based. A rule that wants no special cases can leave it and count
it. Fixture: the method above, expect nothing.

### 3. A suppression grounds does not recognise (1 finding, questdb)

[FuzzTransactionGenerator.java:668](https://github.com/questdb/questdb/blob/514d5f8cc5d17151793eedf29d67ee72aaafa060/core/src/test/java/io/questdb/test/fuzz/FuzzTransactionGenerator.java#L668)

```java
//noinspection lossy-conversions
step *= rnd.nextDouble();
```

**Cause.** `lossy-conversions` is javac's name for exactly this check
(`-Xlint:lossy-conversions`, JDK 20 and later), and the name IntelliJ uses to
suppress it. The author marked the narrowing as intended. grounds matches
`//noinspection X` and `@SuppressWarnings("X")` only against a rule's
`sources` (`crates/grounds-rules/src/runner.rs`, `comment_suppresses` at line
235 and `matches_suppression` at line 298), and this rule's sources are
`errorprone:NarrowingCompoundAssignment` and `sonar:S2164`.

**Reproducer** (synthetic):

```java
import java.util.Random;
class N {
    long a(Random rnd, long step) {
        //noinspection lossy-conversions
        step *= rnd.nextDouble();            // grounds reports; javac -Xlint warns (comments mean nothing to it)
        return step;
    }
    @SuppressWarnings("lossy-conversions")
    long b(Random rnd, long step) {
        step *= rnd.nextDouble();            // grounds reports; javac -Xlint:lossy-conversions is silent
        return step;
    }
}
```

`javac -Xlint:lossy-conversions` (21) warns on `a` and not on `b`;
`grounds check` reports both.

**Proposed fix.** Add the javac lint name as a source of the rule
(`javac:lossy-conversions`), and teach `matches_suppression` and
`comment_suppresses` a `javac:` prefix (the bare name in
`@SuppressWarnings` and after `noinspection`). Fixture: both methods above,
expect nothing.

## A false report of a stable rule

### `missing-jdk-import` (stable in `grounds changed`): Maven `<testRelease>` is ignored (3 findings, prometheus client_java)

[HTTPServerTest.java:22–24](https://github.com/prometheus/client_java/blob/47bc9c7ae40c20715b8eb3bdc65d40f4c2327ded/prometheus-metrics-exporter-httpserver/src/test/java/io/prometheus/metrics/exporter/httpserver/HTTPServerTest.java#L22)
imports `java.net.http.HttpClient`, `HttpRequest` and `HttpResponse`.
grounds: "`java.net.http.HttpClient` is not public API in Java 8". The
[root pom](https://github.com/prometheus/client_java/blob/47bc9c7ae40c20715b8eb3bdc65d40f4c2327ded/pom.xml#L279)
sets `<release>${java.version}</release>` (8) and
`<testRelease>${test.java.version}</testRelease>` (25): test sources compile
for Java 25, where those classes exist. The project builds.

**Reproducer, in change mode** (synthetic): a git repository with a pom
holding `<release>8</release><testRelease>17</testRelease>`, a main class
`p.Main` and a test `p.MainTest`; a second commit adds
`import java.net.http.HttpClient;` and a method returning
`HttpClient.newHttpClient()` to the test.
`grounds changed --base HEAD~1 --no-daemon` reports
`missing-jdk-import src/test/java/p/MainTest.java:2`, **`maturity: stable`**.
`javac --release 8` on the main class and `javac --release 17` on the test
compile both without error.

**Where:** `crates/grounds-engine/src/java_release.rs`: `Poms::evidence`
(line 873) reads `release`/`maven.compiler.release` and `source`/`target`
for a module, and that one release is applied to its main and test sources
alike. `testRelease`, `testSource`, `testTarget` and
`maven.compiler.testRelease`/`testSource`/`testTarget` are not read. (Gradle's
`compileTestJava { options.release = ... }` was not looked at.)

**Proposed fix:** read the test settings and use them for the module's test
sources. Or, unknown means silent: when a module declares any test release
or source, treat the release of its test sources as unknown, so the rule
says nothing there. Session test: the reproducer above, expect no report;
the same commit on the main class still reported.

This does not change any count of the three target rules. It is a bug in
what 0.1.0 promises, found on the way.

## How the findings were judged

- **The three target rules (100 verdicts)** were judged in this session by
  reading each finding's code, its callers and its build files. Each verdict
  shape was confirmed with a synthetic program compiled and run with javac
  and java 21:
  - SLF4J 2.0.16 with slf4j-simple: extra arguments are dropped, an unfilled
    `{}` prints as is, and a trailing `Throwable` is logged as the
    exception, for each of the six message shapes found.
  - AssertJ 3.26.3: `assertThat(false);`, `assertThat(1 == 2);`,
    `assertThat(int)` and `assertThat(false).as("..")` all pass.
  - The three narrowing reproducers above.
- **The other 707 sampled findings** were split by rule over six parallel
  review passes. All had the same instructions, the rule's own definition
  (`grounds explain`) and the earlier reports' verdicts for the same rule as
  calibration, plus the full checkouts to read callers and build files.
- **A seventh, blind pass** re-judged 82 findings without seeing the first
  verdicts: a seeded 10% of the 707 (71), plus every false verdict of a
  target or stable rule (12, one of which was also drawn). It disagreed on 2
  of the 82, neither in a target or stable rule. Both were settled by
  reading the code, and both first verdicts were kept:
  - `optional-get-without-check`, debezium `AbstractChunkQueryBuilder.java:186`,
    kept true: `buildChunkQuery` calls `addLowerBound`, which reaches
    `nullsSortLast.get()`, before it checks `isEmpty()`.
  - `rounding-of-integer-division`, bisq `Base58.java:68`, kept false: the
    `Math.floor` of an integer division is a no-op, but the floor is what the
    code wants. The rule's suggested fix (divide in floating point) would
    change nothing, and the code is not wrong.

  The blind pass agreed with all 7 false `narrowing-compound-assignment`
  verdicts, the 3 false `missing-jdk-import` ones and the 2 false stable-rule
  ones.

## What the numbers support

**`assertj-assertion-without-check`: promote.** On this set alone it has 60
judged findings, all true, and on the two sets it was never tuned on, 68 of
68. Every finding is the same shape: an AssertJ `assertThat(..)` statement
with nothing after it, which a run of AssertJ shows checks nothing. The
caveat: 42 of its 102 findings here were not judged (the sample was 60).

**`log-placeholder-mismatch`: the numbers support promoting it, but not
from this set alone.** This set gives 13 of 13, below the 20 the bar asks
for. The two never-tuned sets together give 21 of 21, and all four sets 28
of 29. Whether two sets may be pooled to reach 20 is the maintainer's call;
the earlier promotion of eight rules (#88) pooled three.

**`narrowing-compound-assignment`: do not promote.** 20 of 27 on this set,
23 of 30 on the never-tuned sets. Six of the seven false reports are values
that cannot lose anything (a one-bit result, `skip(n)` bounded by `n`), and
one is a suppression grounds does not read. Under a looser definition,
where any implicit narrowing counts as true, it would be 26 of 27. Before a
promotion it needs the fixes above and an agreed definition of a true
finding.

**No other preview rule** reaches 20 judged findings on this set, and only
`fixme-comment` does when the four sets are pooled.

**For the stable rules, two things need attention before the next release**:
- `missing-jdk-import` makes a false stable report in `grounds changed` on
  a project with a different Maven test release. The cause and a fix are
  above.
- `public-static-non-final-field` now has 2 false of 32 judged over the four
  sets: deliberate fixtures, but one more than the bar allows when pooled.

## What was not done

- No change mode (`grounds changed` replay of real commits) and no recall run
  on these 40 projects; only the synthetic `missing-jdk-import` commit above.
- 42 of the 102 `assertj-assertion-without-check` findings were not judged.
- The other rules were sampled at 8 each, so this set says nothing about
  promoting them alone. Info rules were not judged.
- The proposed fixes were not made, as the task asked: no product code was
  changed, and no fixture or test was added from these projects.
- `missing-jdk-import`'s cause was checked for Maven only; Gradle's separate
  test compile options were not looked at.
- The sampled findings outside the three rules were judged by review passes
  whose second, blind judgement disagreed on 2 of 82. The precision of a
  sample of 8 carries that much judging noise, and more from which projects
  were drawn.

## How the fourth set was chosen

Written and committed (`84592f6`) before grounds was run on any of these
projects; unchanged since, except this line and the heading of the method.

The first three sets of [corpus/holdout.tsv](../../corpus/holdout.tsv) are
spent. The third ([2026-11c](2026-11c.md)) left three preview rules that were
right every time they were judged but had too few findings to judge:
`narrowing-compound-assignment` (3 findings on that set),
`log-placeholder-mismatch` (13) and `assertj-assertion-without-check` (11).
This fourth set is twice as large, 40 projects, and is picked so that those
three rules get findings. The rules for choosing it:

- **Fresh.** No project is in corpus/projects.tsv, corpus/smoke.tsv or the
  first three sets of corpus/holdout.tsv (checked by owner/name and by
  repository name), and none is a fork (GitHub's `fork` flag was checked for
  every one) or a copy of one of them.
- **Aimed at the three rules.**
  - For `assertj-assertion-without-check`: projects whose tests use AssertJ
    a lot (debezium, spring-integration, spring-data-mongodb,
    spring-session, Strata, reactor-core, reactor-netty, redisson,
    testcontainers, java-operator-sdk, parquet-java, ta4j, XChange,
    prometheus client_java, JsonPath, aircompressor, rocketmq).
  - For `log-placeholder-mismatch`: projects that log heavily through SLF4J
    or Log4j 2 (bisq, debezium, jmeter, openhab-core, shenyu, killbill,
    bookkeeper, xchange, parquet-java, hivemq, canal, ratis, terasology).
  - For `narrowing-compound-assignment`: numeric code, namely codecs
    (aircompressor, jackson-dataformats-binary, commons-imaging, parquet-java,
    bitcoinj), parsers and databases (questdb, JsonPath, canal's binlog
    reader), game engines and servers (Minestom, Terasology, Geyser), maths
    and geometry (commons-math, jts, RoaringBitmap, joda-time) and finance
    (Strata, ta4j, killbill, bisq, XChange).
- **The same mix as before otherwise**: 25 Maven and 15 Gradle builds; from
  about 19,000 to 2.9 million lines; plain libraries, plain Spring
  libraries, Spring Boot applications (shenyu, canal), Micronaut
  (micronaut-kafka), Guice applications (hivemq, bisq, killbill), an OSGi
  platform (openhab-core), desktop applications (jmeter, bisq), and heavy
  Lombok users (xchange, bisq, bookkeeper, testcontainers, geyser).
- **Alive**: every one was pushed to in 2026, all but JsonPath (February)
  and canal (July) within the last month; each is pinned to the head of its
  default branch on 2026-11-11.
- Chosen from what the author knew of the Java ecosystem. After the
  checkouts were fetched, only the counts in the table below were taken
  (files, lines, and files importing AssertJ, an SLF4J or Log4j 2 logger, or
  Lombok); they changed nothing in the list. No project will be dropped or
  added after a run.

`@Slf4j`/`@Log4j2`; lines are all lines of all `.java` files, tests included.

  still shares much of its code; commons-math was taken, so one of the two.

- **apache/pulsar, hazelcast/hazelcast, apache/iotdb**: very large; one very

## Method (as written before the run)

As [scripts/holdout.py](../../scripts/holdout.py) does for the earlier sets:
shallow fetch of the pinned commit, `[classpath] scan_caches = false` in a
`grounds.toml` where there is none, no build and no jars, a release build of
master, `grounds check --format json`.

- The three target rules: every finding is judged, up to 60 per rule; above
  60, a seeded sample of 60 (`--seed 1`), said so in the results.
- Every other preview rule of severity warning or error with findings: a
  seeded sample of 8 (`--sample 8 --seed 1`), as the earlier reports did.
- Every verdict has a reason, true ones included, in
  [2026-11d.tsv](2026-11d.tsv). Where it is cheap, a verdict is confirmed with
  a small synthetic reproducer compiled and run with javac/java (never
  project code).
- Nothing found here is turned into a fixture or a test, and no product code
  is changed by this task.

Reproduce:

    python3 -I scripts/holdout.py --dir DIR --after 'fourth set, 2026-11'
    python3 -I scripts/holdout.py --dir DIR --after 'fourth set, 2026-11' --sample 8 --seed 1 \
        --all narrowing-compound-assignment,log-placeholder-mismatch,assertj-assertion-without-check --all-max 60
