# Hold-out recall, November 2026: when a change breaks other files, does grounds say so?

grounds 0.0.12 (release build of master at `5316324`), run the way CI and the
agent hooks run it: `grounds changed --base HEAD~1`, after one commit of edits,
on the 40 projects of [corpus/holdout.tsv](../../corpus/holdout.tsv) at their
pinned commits, which the rules were never tuned on. The
[replay](2026-11-replay.md) found no false break report in 514 real commits:
when grounds says a change broke another file, there is no evidence that it is
wrong. This report measures the other half: **when a change certainly breaks
another file, how often does grounds say so, and why does it not when it does
not?** It measures only. No rule, fixture or line of Rust was changed because
of it, and nothing from these projects was made into a fixture or test.

## Headline

1. **2,367 edits that break other files; grounds reported 1,993 (84%).** Ten
   kinds of edit, up to 6 of each per project, each chosen so that it
   certainly breaks compilation of at least one other file (the ways each kind
   is known to break are below). "Reported" means `changed --base` named a
   place in another file as broken (`pending`), or a compile-break finding in
   another file, or a `breaks-other-files` finding on the changed line. For
   1,944 of the 1,993 the reports include a place the edit was chosen to
   break.
2. **By kind the picture is uneven.** Renamed, removed, re-parametrised or
   privatised methods, methods removed from an interface, deleted or renamed
   classes: 95–99% reported. Renamed fields and constants: 90%. A new abstract
   method that existing implementations lack: 66%. A changed return type
   whose result a caller uses: **7%**. Without the return-type kind, 1,977 of
   2,129 (93%).
3. **The compiler agrees with the choice of edits.** javac (JDK 21, on the
   files expected to break, without dependency jars or annotation processing)
   rejected 2,060 of the 2,367 edited trees with a new error in a file expected
   to break; for the other 307 the expected files already had errors from
   missing jars that hide the call (it never compiled one of them cleanly), so
   they are unconfirmed, not refuted. Of the 2,060 confirmed, grounds reported
   1,751 (85%). No project's own build ran (see "What was not done").
4. **No false alarm.** 480 edits that break nothing (12 per project) got no
   report at all. The replay's 514 real commits had none either.
5. **The daemon does not always agree with a fresh run.** It did on 3,003 of
   the 3,074 edits asked both ways. On 62 it reported fewer broken places than
   `--no-daemon` (on 9 of them none at all), always after an earlier edit had
   deleted or renamed a file that `git reset` then brought back; on 9 (all
   dataease) it reported more. Both are bugs in how the daemon follows files;
   see "Daemon and fresh run".
6. **374 breaks were not reported. 248 of them are gaps that can be fixed**,
   71 are silence that is right without jars or without a JDK of the project's
   release, and 55 are partly each. The largest gap is the return-type kind
   (213 of its 222 misses); the next is one project, dataease, whose whole
   backend is tracked by git but listed in `.gitignore`, so grounds never reads
   it (46 misses).

## How it was measured

[scripts/ci_mutations.py](../../scripts/ci_mutations.py) gained `--kinds`:
edits that certainly break another file, each one commit on top of the
checkout, after which `grounds changed --base HEAD~1` is asked, through the
daemon (which has followed every edit so far) and with `--no-daemon`, and the
checkout is reset. Its existing behaviour (`--safe`, `--breaking`, used by
corpus.yml) is unchanged: on spring-petclinic-rest it makes the same 18 edits
with the same result as before (`safe 12 (0 reported), breaking 6 (6
reported)`).

A candidate is kept only when a scan of the sources (comments and string
literals blanked, braces matched) finds a use in another file that certainly
reaches the edited declaration: the other file imports the type by its
qualified name or is in its package without an import of another type of
that name, and declares no type of that name; the receiver is the type itself
or a variable all of whose declarations in that file have that type and that
is no lambda parameter or inherited field; the member is the only one of its
name in the type and all its supertypes, which must all be project types or
JDK types whose members are listed (`Object`, `Serializable`, `Comparable`,
`Runnable`, `Closeable`, the common exceptions). Records, members Lombok may
generate, and names of `Object` and `Enum` methods are left out. Where that
was not certain the candidate was skipped. The kinds, and why each breaks:

| kind | edit | why another file stops compiling |
|---|---|---|
| rename-method | `m` → `mZzRenamed` | `x.m(..)` names a method the type no longer has |
| remove-method | the declaration deleted | the same |
| add-parameter | `int` parameter appended (never to varargs) | the only `m` now takes one argument more than the call passes |
| change-return | return type → `Void`, body → `throw` | the caller declares a variable of exactly the old type from the result, calls a method on it that `Object` lacks, or negates it; `Void` is final and implements nothing |
| make-private | `public` → `private` (non-abstract, in a class) | another top-level class cannot access it |
| delete-class | the file of a public top-level type deleted | a single-type import of it, or a same-package use (`new C(`, `C.x`, a declaration, `extends`/`implements`) in a file without on-demand imports; never a `java.lang` name; the package keeps other files |
| rename-class | the type, its file and its own references renamed | the same |
| interface-remove-method | an abstract method of an interface deleted | a call through a variable of the interface type |
| add-abstract-method | `void zzMutAbstractN();` added to an interface or abstract class | a non-abstract class in another file implements (extends) it directly, or an anonymous class does |
| rename-field | a public field or constant renamed | `C.NAME` or `x.NAME` in another file, `C` having no nested type of that name |

Every project was set up as [scripts/holdout.py](../../scripts/holdout.py)
does: shallow fetch of the pinned commit, `[classpath] scan_caches = false`
in a `grounds.toml` (none of the 40 has one), no build, no jars. The JDK is 21;
six projects (akhq, conductor, graphhopper, kafka-ui, kestra, velocity) target
Java 25, and grounds warns about that on every run. Per project: 12 safe
edits, the 6 existing `--breaking` renames, then up to 6 of each kind
(`--safe 12 --breaking 6 --kinds all --per-kind 6 --daemon`); some projects
had fewer candidates of a kind. 3,074 edits in all, each asked twice.

Two defects of the script were found and fixed while running, and the edits
they touched were made again: a removed method's annotations were left behind
(remove-method and interface-remove-method of the first nine projects; the
file then did not parse), and a file with CRLF line ends was rewritten with
LF, so that git saw every line as changed (all of dataease, two edits of
apicurio-registry). The numbers here are from the corrected runs; the TSV has
only those.

The compiler check: `--confirm REPORT --build-dir COPY --javac` replays every
edit on a separate clone (so that no build output ever lands where grounds
looks) and runs javac on the files expected to break plus the edited files,
with every module's source roots on the source path, before and after the
edit. An edit counts as confirmed when javac reports an error in an expected
file that it did not report before. The projects' own builds (Maven, Gradle
wrappers) were not run; see "What was not done".

Every edit is a row of [2026-11-recall.tsv](2026-11-recall.tsv): kind, the
edited declaration with a permalink, the number of places expected to break and
one of them, whether grounds reported the break, by which rules, whether the
daemon agreed, javac's result (`confirmed`, `unconfirmed`, or `refuted`, which
never occurred) and, for a miss, its cause (named as in the table of causes).

## Safe edits

480 edits that cannot break anything (a new private or public method with a
fresh name, a comment line that shifts the file, a new class in an existing
package; 12 per project): **no report on any of them**, through the daemon or
not. There is no false alarm to show.

(A first run of dataease got two `unused-private-field` warnings after a safe
edit. They were the script's doing, not grounds': the file had CRLF line ends
and the script rewrote it with LF, so every line had changed. The fields are
in fact unused. With the line ends kept the edit gets no report.)

## Why breaks were not reported

All 374 misses were looked at: for each, the source at the places expected
to break and the output of a small probe program (built in a scratch
directory against the grounds crates, not committed) that prints, for a call
or field access on a line, the receiver's symbol and type and the first
condition of `closed_class` that fails, or, for a class, why its hierarchy is
not closed and which inherited abstract methods have parameter types it does
not know. Each cause below was then reproduced on a small synthetic project
(none of it project code). Ranked by misses:

| # | cause (as named in the TSV) | misses | kinds | projects | silence is |
|---:|---|---:|---|---:|---|
| 1 | `void-receiver`: a method called on a result whose type is a JDK class | 86 | change-return | 34 | a gap |
| 2 | `assign-not-cross-file`: `incompatible-assignment` is not run on other files in change mode | 61 | change-return | 27 | a gap |
| 3 | `assign-not-judged`: an assignment `incompatible-assignment` does not judge (primitive, generic, array or unknown target) | 55 | change-return | 27 | partly right, partly a gap |
| 4 | `ignored-but-tracked`: the calling file is tracked by git but matched by `.gitignore` | 46 | all ten | 1 (dataease) | a gap |
| 5 | `jdk-older`: the project targets Java 25 and the JDK is 21 | 37 | eight kinds | 6 | right |
| 6 | `library-supertype`: a supertype comes from a jar that is not there | 33 | add-abstract-method | 17 | right |
| 7 | `abstract-unknown-params`: `unimplemented-abstract-method` gives up when any inherited abstract method has a parameter of unknown type | 26 | add-abstract-method | 16 | a gap |
| 8 | `negation-unchecked`: a negated result (`!x.isOk()`) | 11 | change-return | 10 | a gap |
| 9 | `annotation-value`: a constant read inside an annotation | 8 | rename-field | 5 | a gap |
| 10 | `anonymous-class`: the implementation is an anonymous class or an enum constant's body | 7 | add-abstract-method | 6 | a gap |
| 11 | `suppressed-all`: the calling class has `@SuppressWarnings("all")` | 3 | rename-method, add-parameter, change-return | 2 | a gap |
| 12 | `lombok-open`: a Lombok annotation the model does not reproduce (`@Accessors`) on the edited class | 1 | rename-method | 1 | right |

Causes 1, 2, 3 and 8 are the return-type kind (213 of its 222 misses; the
other 9 are causes 4, 5 and 11). The return-type kind uses `Void` because it
converts to nothing, so that the break is certain; real return-type changes
(to `Optional<T>`, to a `String`, to a list) reach the same places in grounds.

### 1. A method called on a result whose type is a JDK class (86)

The edit made a method return `Void`; a caller calls a method on the result
(`visit.getPet().getId()`, `config.getTtl().toJavaTime()`).

```java
// before: public Pet pet()        after: public Void pet() { throw new UnsupportedOperationException(); }
int a(Svc s) { return s.pet().id(); }   // javac: cannot find symbol id(); grounds: silent
```

Silent in `crates/grounds-rules/src/rules/resolution.rs`, `closed_class`
(`if !c.is_source() ... return None`), reached from
`UnresolvedMethod::check_node`: a receiver that is not a project class is
never judged. **A gap.** When the project's release is not newer than the
JDK, the JDK's API is read exactly from `ct.sym`
(`Classpath::exact_jdk_release`, which `missing-jdk-import` already relies
on). Proposed fix: let `closed_class` accept a `java.*` class whose whole
hierarchy is JDK classes when `exact_jdk_release()` is `Some`; a class from a
jar stays unknown. Example: [airlift KeystoreSecretProvider.java:38](https://github.com/airlift/airlift/blob/cf5998126dc0b50ae41c60c32baf19b49ea64ed2/secrets-keystore-plugin/src/main/java/io/airlift/secrets/keystore/KeystoreSecretProvider.java#L38).

### 2. `incompatible-assignment` is not run on other files in change mode (61)

The caller declares a variable of the old return type
(`OmsContainer c = OmsContainerFactory.fetchContainer(id, null);`). `grounds
check` on the edited tree reports `incompatible-assignment` there; `grounds
changed --base` does not.

```java
void b(Svc s) { Pet p = s.pet(); }   // grounds check: incompatible-assignment; grounds changed --base: nothing
```

Silent in `crates/grounds-engine/src/session.rs`, `CROSS_FILE_RULES`, the
rules `Session::cross_file_breaks` runs on the unchanged files:
`incompatible-assignment` is not in the list, and neither is
`unresolved-static-import` (a statically imported method renamed: `grounds
check` reports the import, `changed --base` says nothing; reproduced, but no
edit of this measurement used a static import, so it has no count here).
**A gap.** Proposed fix: add both rules to `CROSS_FILE_RULES`. Neither rule
appears among the findings judged in [2026-11](2026-11.md) and
[2026-11b](2026-11b.md), so there is no measurement of their precision on
unseen code in either direction; change mode keeps only findings that are new
against the base version. Example: [apicurio-registry SubjectsResourceImpl.java:551](https://github.com/Apicurio/apicurio-registry/blob/7bde57ebc79806a4a01f02830f8c9f788dbb7a84/app/src/main/java/io/apicurio/registry/ccompat/rest/v7/impl/SubjectsResourceImpl.java#L551).

### 3. An assignment `incompatible-assignment` does not judge (55)

The target is a primitive (`int n = ...`), a generic type (`Set<String> s =
...`), an array, or a type from a jar or from generated sources
(`ResponseEntity<Resource>`, `TopicMessageDTO`). Even `grounds check` is
silent.

```java
void d(Svc s) { List<String> n = s.names(); }   // names() now returns Void: javac error; grounds: silent
```

Silent in `crates/grounds-rules/src/rules/resolution.rs`,
`IncompatibleAssignment::check_node` (`if !args.is_empty() { return; }`, the
`Ty::Class` match on the target, `if !known(got) || !known(want)`). **Partly
right, partly a gap.** When the returned type could be a subtype of an
unknown target, silence is right. But a returned type that is a final class
with a fully known hierarchy (`Void`, `String`, a final project class) is
assignable only to its own supertypes, so any target outside them is
certainly incompatible, generic or unknown; and a reference type that is not
a boxed primitive never converts to a primitive. Proposed fix: judge those
two cases (by the target's erasure). Example: [akhq SchemaRegistryRepositoryTest.java:165](https://github.com/tchiotludo/akhq/blob/63f53051ae2df1dedfd57caa91a78674e9c5ccd4/src/test/java/org/akhq/repositories/SchemaRegistryRepositoryTest.java#L165).

### 4. The calling file is tracked by git but matched by `.gitignore` (46)

dataease's `.gitignore` lists `/core/core-backend/`, yet git tracks its 436
Java files: the whole backend. grounds finds files with `.gitignore` applied,
so it analyses 810 of the 1,246 tracked files, and nothing that breaks a
caller in the backend is reported (14 of dataease's 60 breaks were). The same
holds for 4 tracked files of vertx-sql-client, which no edit here reached.

Silent in `crates/grounds-engine/src/workspace.rs`, `Workspace::discover`
(`ignore::WalkBuilder` with `.git_ignore(true)`). **A gap.** What a build
compiles is what is checked out, ignored or not. Proposed fix: in a git
repository, add the files `git ls-files` lists to what the walk finds (or
take the Java files from `git ls-files` plus the untracked files that are not
ignored). This also explains dataease's daemon differences (below). It also
means the [replay](2026-11-replay.md) never looked at dataease's backend.
Example: [dataease VisualizationExcelUtils.java:174](https://github.com/dataease/dataease/blob/195a2f35b65f459a42545514a26562329975dd1a/core/core-backend/src/main/java/io/dataease/visualization/utils/VisualizationExcelUtils.java#L174).

### 5. The project targets Java 25 and the JDK is 21 (37)

grounds then treats every JDK class but `Object` as possibly having members
it cannot see, so a project class with any JDK supertype (`Closeable`,
`Serializable`, `Enum`, an exception) has an incomplete hierarchy and the
compile-break rules say nothing about it. It warns about this on every run.

```java
// grounds.toml: java_release = 25; JDK 21
public class Svc implements java.io.Closeable { public String findX(String s) {...} public void close() {} }   // was find()
String a(Svc s) { return s.find("x"); }   // silent; with java_release = 21 it is reported
```

Silent in `crates/grounds-index/src/hierarchy.rs`,
`ClassLookup::hierarchy_complete` (through `may_lack_members`,
`crates/grounds-index/src/index.rs`). **Right**: a JDK 25 interface could
declare a default method of that name. The remedy is what the warning says,
`java_home` pointing at a JDK of the project's release. These 37 misses are
why the six Java 25 projects are at 79% against 85%. Example: [akhq FindSchemasForTopicArguments.java:9](https://github.com/tchiotludo/akhq/blob/63f53051ae2df1dedfd57caa91a78674e9c5ccd4/src/main/java/org/akhq/mcp/model/FindSchemasForTopicArguments.java#L9).

### 6. A supertype comes from a jar that is not there (33)

All are add-abstract-method: the implementing class also extends a library
class (MyBatis-Plus `ServiceImpl<M, T>` in pig and mall4j, Netty's
`ChannelDuplexHandler`, Spring's `AbstractResource`), or the edited interface
extends a library interface.

```java
public interface Store extends org.lib.Base { void put(String s); void added(); }   // added() is new
public class FileStore implements Store { public void put(String s) {} }            // javac error; grounds: silent
```

Silent in `closed_class` (`hierarchy_complete` is false). **Right** under
"unknown means silent": the library class could implement the method. The
remedy is the classpath (`grounds classpath`); this measurement ran without
jars on purpose. Example: [commons-compress SevenZFile.java:78](https://github.com/apache/commons-compress/blob/54f0e8ea790923a60812173b8e79b520da9da901/src/main/java/org/apache/commons/compress/archivers/sevenz/SevenZFile.java#L78).

### 7. `unimplemented-abstract-method` gives up on the class (26)

The implementing class is closed, the new abstract method has no parameters,
but another abstract method of the interface takes a type from a jar
(`Mono<Void> handle(WebFilterExchange e, ...)`), and the rule returns before
it looks at the new one.

```java
public interface Handler { boolean applies(String p); void handle(org.example.web.Exchange e); void added(); }  // added() is new
public class Impl implements Handler { public boolean applies(String p) { return true; } public void handle(Exchange e) {} }
// javac: Impl does not override added(); grounds: silent, and reported once handle(Exchange) is gone
```

Silent in `crates/grounds-rules/src/rules/resolution.rs`,
`UnimplementedAbstractMethod::check_node` (`if m.method.params.iter().any(|p|
p.ty.has_unknown()) { return; }`). **A gap**: whether `added()` is
implemented does not depend on the types of `handle`'s parameters. Proposed
fix: `continue` instead of `return`, leaving only that one method unjudged.
Example: [async-http-client DefaultKeepAliveStrategy.java:30](https://github.com/AsyncHttpClient/async-http-client/blob/01044b453f2836360512958535e66ec5a10d3a7d/client/src/main/java/org/asynchttpclient/channel/DefaultKeepAliveStrategy.java#L30).

### 8. A negated result (11)

```java
boolean c(Svc s) { return !s.ok(); }   // ok() now returns Void: javac: bad operand type; grounds: silent
```

No rule checks the operand of `!` (nor a condition of `if`, `while`, `&&`).
**A gap.** Proposed fix: a check, next to `IncompatibleAssignment` in
`crates/grounds-rules/src/rules/resolution.rs`, that a call used as a
condition or as an operand of `!`, `&&`, `||` returns `boolean` or `Boolean`
when its owner is closed and its return type is a known class. Example:
[graphhopper GHMatrixAbstractRequester.java:300](https://github.com/graphhopper/graphhopper/blob/3b2a7eaaaffcd6a60625923a979c7c5d07face02/client-hc/src/main/java/com/graphhopper/api/GHMatrixAbstractRequester.java#L300).

### 9. A constant read inside an annotation (8)

```java
public class Ctl { @Job(weight = Weight.SMALL) void a() {} }   // Weight.SMALL renamed: javac error; grounds: silent
```

Silent in `crates/grounds-rules/src/rules/resolution.rs`,
`UnresolvedField::check_node` (returns when any ancestor is an
`annotation`). **A gap**: an annotation argument is an ordinary constant
expression. Proposed fix: skip only imports and package declarations.
Example: [mall4j ConfirmOrderListener.java:53](https://github.com/gz-yami/mall4j/blob/c69b6793ef2c7f528c5e7364aecd22f0b9f7209f/yami-shop-api/src/main/java/com/yami/shop/api/listener/ConfirmOrderListener.java#L53)

### 10. An anonymous class or an enum constant's body (7)

```java
Filter f = new Filter() { public int apply(int x) { return x; } };   // Filter gained added(): javac error; grounds: silent
```

Silent in `UnimplementedAbstractMethod`
(`crates/grounds-rules/src/rules/resolution.rs`): its `kinds` are the class,
enum and record declarations, so the body of a `new I() { ... }` is never
visited, and an enum whose constants have bodies returns early. **A gap.**
Proposed fix: visit `object_creation_expression` nodes with a `class_body`,
the instantiated type as their supertype, and check each enum constant body
against the enum's abstract methods. Example: [gson ToNumberPolicy.java:36](https://github.com/google/gson/blob/a961b0fe088f8558d00cc1b56e506a3656907a91/gson/src/main/java/com/google/gson/ToNumberPolicy.java#L36).

### 11. `@SuppressWarnings("all")` on the calling class (3)

```java
@SuppressWarnings("all") class Use { String a(Svc s) { return s.find("x"); } }   // find() renamed: javac error; grounds: silent
```

Silent in `crates/grounds-rules/src/runner.rs`, `matches_suppression`
(`v == "all"`), which applies to every rule. **A gap**: javac lets no
annotation suppress an error, and a CI that stays green on a build that does
not compile helps no one. Proposed fix: `"all"` (and the other tools' keys)
do not suppress the compile-break rules; `"grounds"` and the rule's own id

powerjob's `Address` has `@Accessors(chain = true)`, so its members are open

**Right.** Example: [powerjob AddressTest.java:20](https://github.com/PowerJob/PowerJob/blob/d92ad66277ca54e14e2835b2e5a6aaf01f620684/powerjob-remote/powerjob-remote-framework/src/test/java/tech/powerjob/remote/framework/base/AddressTest.java#L20).

## Daemon and fresh run

The two answers were compared field for field after every edit, 3,074 times.
They differed 71 times, on 28 projects.

- **62 times the daemon reported fewer broken places** (on 9 of them none,
  where the fresh run reported the break). Every one came after an earlier
  edit of the same run had deleted or renamed a file, which `git reset` then
  restored. `Session::sync` (`crates/grounds-engine/src/session.rs`) drops a
  file that disappears from its modification times and from the index; when
  the file comes back it is read again only if it is among the changed files
  of a later request. Until then its classes are missing from the daemon's
  index: `removed_class_uses` finds no stub for it, and other files' types
  that mention its classes become unknown, so `override-matches-nothing` and
  `unimplemented-abstract-method` stay silent there. Reproduced on a
  three-file project: delete `Req.java`, restore it, then add an abstract
  method to an interface whose implementation takes a `Req`: `--no-daemon`
  reports `BizImpl does not implement Biz.added()`, the daemon nothing. A
  branch switch or `git stash` does the same to an agent's daemon. Proposed
  fix: keep files that disappeared in `mtimes` (as missing), so that their
  return is noticed like any other change, or compare the workspace's file
  list with the disk on each sync.
- **9 times (all dataease) the daemon reported more**: places in the ignored
  `core/core-backend/` (cause 4). `Session::sync` adds every changed file it
  does not know to the workspace, ignored or not, so once an edit had touched
  a backend file the daemon analysed it while a fresh run still skipped it.

## What the numbers support saying in the README

A paragraph the README could carry about change mode:

> In change mode (`grounds changed --base`) the compile-break rules were
> measured on 40 projects they were never tuned on, with no dependency jars.
> After 514 real commits and 480 edits that break nothing they reported no
> break at all, so a report is not known to be wrong. After 2,367 edits each
> of which breaks another file (2,060 of them confirmed with javac), they
> reported 1,993 (84%): 95–99% of renamed, removed, re-parametrised or
> privatised methods, of methods removed from an interface and of deleted or
> renamed classes; 90% of renamed fields and constants; 66% of abstract
> methods added to a type with implementations; 7% of return-type changes.
> Silence is therefore not evidence that nothing broke, least of all after a
> return-type change or a new abstract method, and in a project whose release
> is newer than the installed JDK.

What they do not support: any recall with the dependency jars on the
classpath (not measured; the misses of causes 5 and 6 would change), or for a
project whose release the JDK covers when it is newer (only one JDK was
used); a recall "for breaking changes" in general (the ten kinds were chosen
so that the break is certain, not drawn from real changes, and real changes
mix kinds in proportions not measured here); recall for constructors,
overloads, generic signatures, static imports, visibility other than
`private`, or breaks in other modules' build files; whole-project mode
(`grounds check`); and that the daemon answers like a fresh run: it did not
on 71 of 3,074 edits. Nor do they support a statement about stable rules: no
rule's precision bar is set by this.

## What was not done

- **No project was built with its own build.** Running the projects' Maven
  and Gradle wrappers was refused by the environment's permission check
  (they run the projects' own code). The compiler confirmation used the JDK's
  javac directly, without dependency jars or annotation processing; that is
  why 307 edits are unconfirmed. None of those 307 had expected files that
  javac compiled cleanly before the edit, so none is refuted; but they are
  confirmed only by the choice of the edit, not by a compiler.
- **One JDK (21).** The six Java 25 projects were not run against a JDK 25.
- **At most 6 edits of each kind per project**, chosen at random among the
  candidates with a fixed seed (`--seed 1`). A project with fewer candidates
  of a kind has fewer.
- **No static-import, constructor or overload edits**; the static-import gap
  (cause 2) was found by reading the code and reproduced, not counted.
- **The daemon followed one sequence of edits per project.** How often its
  stale state shows up in other sequences was not measured.
- **The existing `--breaking` renames were not checked with javac**; their
  67% is a statistic over edits some of which break nothing.

Reproduce: fetch each project of corpus/holdout.tsv at its pinned commit with
`git fetch --depth 1` and add `[classpath]\nscan_caches = false` as
`grounds.toml`, then

    python3 -I scripts/ci_mutations.py DIR --safe 12 --breaking 6 --kinds all --per-kind 6 --daemon --out P.json
    python3 -I scripts/ci_mutations.py --confirm P.json --build-dir CLONE --javac --per-kind 100 --out P.javac.json

where CLONE is a separate clone of DIR at the same commit. The first exits 1
when the daemon and a fresh run disagreed, and still writes P.json. Two
projects ran at a time on a 4-core machine; the whole run took about four
and a half hours.
