# Hold-out precision, November 2026 (second set)

grounds 0.0.12 (master at `acb4c3a`), run on 20 open-source Java projects that
are in none of [corpus/projects.tsv](../../corpus/projects.tsv),
[corpus/smoke.tsv](../../corpus/smoke.tsv) and the first set of
[corpus/holdout.tsv](../../corpus/holdout.tsv). The
[first measurement](2026-11.md) found most compile-break and wiring findings
false. The fixes merged since then were made against its 20 projects, so that
set can no longer measure anything. This second set measures the same way, so
the two can be compared. **It measures only.** No rule, fixture or line of
Rust was changed because of it.

Reproduce: `python3 -I scripts/holdout.py --after 'second set, 2026-11'` (fetch, run), then
`python3 -I scripts/holdout.py --after 'second set, 2026-11' --sample 8 --seed 1`
(sample). Every verdict is in [2026-11b.tsv](2026-11b.tsv) (rule, project,
path, line, verdict, reason), with a reason for every verdict, true ones included.

No cause the first report named comes back. But the new set brings new ones:
224 findings on 5 of the 20 projects, and all 224 are false. Fifteen projects
get no compile-break or wiring report at all. Ranked by false reports:

## Ten rules that most need attention, across both measurements

Selection: rules whose samples are at most half true on both sets, ranked by
the false findings the two samples imply together (findings × false share,
summed over both sets). Error rules come first because an error claims more.
"x/y" is true of judged, first set then second set. `unresolved-method` is
left out: its 211 false reports on the first set came from causes that have
been fixed, and the second set has only one finding (false).

1. **`bean-not-found`** (error): 0/45, then 0/193. Every finding on both sets
   is false, each time from different causes. First set: Guice, Sisu, Quarkus,
   Micronaut scopes, HK2. Second set: meta-annotated factory methods,
   `@MapperScan` wildcards, nested bean classes. The bean model does not yet
   cover enough ways of registering a bean to say "no bean" on unseen code.
2. **`null-dereference`** (error): 0/8, then 0/8 (51 and 52 findings). Again
   every sampled case needs a correlation the analysis does not track: a
   variable known non-null from another check, a callee that always throws
   (`_reportArgumentError`, `LettuceAssert.notNull`), or an XOR precondition
   (`checkArgument(a == null ^ b == null)`).
3. **`null-passed-to-nonnull-parameter`** (error): 0/8, then 0/8. Tests that
   pass `null` on purpose: to check a bean-validation `@NotNull` violation, to
   call a method that throws regardless, or as the only value of `Void`.
4. **`unresolved-field`** (error): 0/7, then 0/30. Second set: Lombok builder
   fields and `@FieldNameConstants`.
5. **`test-without-assertion`** (warning): 4/8, then 2/8. The highest-volume
   warning (486 and 394 findings). Most false cases are deliberate
   "does not throw" tests.
6. **`lost-stack-trace`** (warning): 4/8, then 2/8 (259 and 220 findings).
   Deliberate translation into a user-facing or protocol exception, and
   exceptions that cannot happen (UTF-8, SHA-1).
7. **`resource-leak`** (warning): 1/8, then 3/8 (232 and 134 findings).
   In-memory closeables again (a mock `FileChannel`, an `InMemoryStorage`), plus
   ownership handed to another object and a resource closed by a following
   try-with-resources.
8. **`identical-branches`** (warning): 4/8, then 3/8 (114 and 85 findings).
   Per-type dispatch tables, pattern-matching `case` labels with their own
   bindings that cannot be merged, and branches that are not adjacent.
9. **`mutable-enum-field`** (warning): 2/8, then 2/8 (49 and 66 findings).
   `private` fields assigned only in the constructor, with no setter.
10. **`singleton-mutable-state`** (warning): 0/8, then 2/8. Configuration
    setters, lazily initialised fields under `synchronized`, and a field written
    only by one `@Scheduled` job.

Close behind: `static-field-written-from-instance-method` (2/8, 0/8: the
`ApplicationContextAware` static-holder idiom), `component-on-abstract-type`
(0/8, 1/8: Dagger's `@dagger.Component` is still taken for Spring's
`@Component`, in 22 of nomulus's 23 findings; the first report named this
cause, and it was not among the fixes), `switch-fallthrough` (3/8, 0/8),
`compareto-specific-value` (0/8, 0/5, all `BigDecimal.compareTo` again) and
`infinite-loop` (0/2, 0/8: deliberate worker and benchmark loops).

Two rules differ with p < 0.05. Both rest on very few findings, and each
side's sample comes from one project:

## Totals

- **21,351 findings** over 20 projects (20,734 Java files, 3,181,859 lines). By
  reported severity: 323 error, 3,431 warning, 17,597 info. By catalogue
  severity, which is what the sample was drawn by: 375 / 3,446 / 17,530.
- **94 rules** of severity error or warning have findings. All of them were
  judged: the 3 hard rules with findings completely (224 findings), and 91
  others with up to 8 sampled findings per rule, spread over projects (seed 1;
  470 findings). **694 verdicts** in all. Info rules were skipped.
- The 224 compile-break and wiring findings were judged in this session by
  reading the code at each finding and the bean or member it refers to. The 470
  sampled findings were split over five parallel review passes with the same
  instructions and the first report's verdicts as calibration. Then every one
  of their 236 false and unclear verdicts was read in this session, and a random
  10% of their true verdicts (23 of 234, seeded) was re-judged in the code.
  **No verdict changed.** Two reasons had been swapped between rows and were
  corrected. One re-judged true verdict is borderline and was kept:
  `equals-without-hashcode` on commons-compress `AttributeLayout`, which
  overrides `hashCode` but keeps identity `equals`. That breaks no contract,
