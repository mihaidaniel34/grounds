# Hold-out precision, November 2026

grounds 0.0.12 (master at `f043060`), run on 20 open-source Java projects that
are not in [corpus/projects.tsv](../../corpus/projects.tsv) and that no rule
was ever tuned on. Every false positive found on the 26 corpus projects
became a fixture and was fixed, so precision there says little about other
code. This is the first measurement on code the rules have not seen. **It
measures only.** No rule, fixture or line of Rust was changed because of it.
A fix made from these cases would make this set worthless as a hold-out.

Reproduce: `python3 -I scripts/holdout.py` (fetch, run), then
`python3 -I scripts/holdout.py --sample 8 --seed 1` (sample). Every verdict
is in [2026-11.tsv](2026-11.tsv) (rule, project, path, line, verdict, reason).

**Setup caveat.** There was no `grounds classpath` step and no build, so each
checkout had only `scan_caches = false` and the JDK (21), with no dependency
jars. Calls into libraries stayed unresolved, and grounds says so on stderr
for every project. Four projects target Java 25, newer than the JDK. Recall
was low, but by the "unknown means silent" design precision should not have
suffered. The results below show that this does not hold for the DI rules or
for project-internal resolution.

## Five rules that most need attention

1. **`unresolved-method` (and `unresolved-constructor`, `unresolved-field`): 15
   true of 243, all in files that are never compiled.**
   - On apache/maven, 183 reports come from one cause (169 `unresolved-method`,
     8 `unresolved-constructor`, 6 `unresolved-field`). A test-resource fixture
     (`its/core-it-suite/src/test/resources/mng-3503/.../org/codehaus/plexus/util/xml/Xpp3Dom.java`)
     declares a stub class with the same fully qualified name as the
     plexus-utils class. grounds resolves every `Xpp3Dom` use in the build to
     the stub. Another 29 reports have the same root: two copies of
     `AbstractMavenProjectTestCase`, `AbstractCoreMavenComponentTestCase`,
     `AbstractDependencyMojo` and `TestComponent` in different modules or
     fixtures, with grounds picking the wrong one. A class name declared more
     than once in a project appears to be resolved without regard to the
     module doing the lookup.
   - Two smaller causes:
     - Modello Velocity templates under `src/mdo/java/*.java` are analysed as
       Java (11 reports).
     - A Lombok `@AllArgsConstructor(staticName = "of")` next to hand-written
       `of(...)` overloads: grounds does not see the generated
       `of(String, String, Object)` (5 reports, jetlinks).
2. **`bean-not-found`: 0 true of 45.** The wiring model treats every
   JSR-330 project as annotation-scanned and misses beans registered any
   other way:
   - Guice/Sisu module `bind()` and Maven 4's own `org.apache.maven.api.di`
     (18 on maven).
   - Quarkus producer classes without a scope annotation, `@ConfigMapping`,
     `@RegisterRestClient`, `@RegisterAiService` and build-step synthetic
     beans (13 on apicurio-registry).
   - Micronaut `@RequestScope` (7 on akhq).
   - HK2 `AbstractBinder` (graphhopper) and Guice in a library module (shiro).
3. **`ambiguous-bean`: 0 true of 15.**
   - Spring: a `@Bean` method and a `@Component` class with the same bean
     name are one bean, not two (6 on stirling-pdf).
   - Sisu/Guice: several implementations of an unqualified type are not an
     error; the highest-ranked one is injected (9 on maven).
4. **`null-dereference` (error in the catalogue, reported as warning): 0 true
   of 8 sampled, 51 findings.** Every sampled case needs a correlation the
   analysis does not track:
   - a boolean computed from a null check earlier;
   - a callee that throws on null;
   - one flag guarding both the null assignment and the use;
   - a loop bound of 0 when the array is null;
   - a `@Nullable` generic return whose supplier cannot return null.
5. **`resource-leak`: 1 true of 8 sampled, 232 findings.** It is the
   highest-volume warning with low precision:
   - in-memory closeables (`StringReader`, `JsonReader`, a jsoup `StreamParser`
     over a String, heap `RAMIntDataAccess`);
   - a `Serde` whose `close()` is a default no-op;
   - `@SuppressWarnings("resource")`, which is ignored;
   - a class loader that must stay open;
   - a container-owned response stream.

Other rules with no true finding in their sample deserve a look too. Each has
a single clear cause:

| rule | severity | true in sample | cause |
|---|---|---|---|
| `compareto-specific-value` | error | 0/8 | all `BigDecimal.compareTo`, documented to return -1, 0 or 1 |
| `for-loop-updates-wrong-variable` | error | 0/8 | `for (Iterator it = …; it.hasNext(); i++)` with a separate counter |
| `null-passed-to-nonnull-parameter` | error | 0/8 | tests passing `null` for collaborators the tested path never uses |
| `component-on-abstract-type` | warning | 0/8 | Dagger's `@dagger.Component`, which must be on an interface, taken for Spring's `@Component` |
| `singleton-mutable-state` | warning | 0/8 | fields written once at startup through `*Aware` setters, `@PostConstruct` or config setters |

The sample precisions treat each rule equally. Weighting each rule's sample
precision by its number of findings gives an estimate of what a user would
see. It is only an estimate, because a rule's 8 findings stand for up to 486:

- about **66%** for warning findings (3,191 findings);
- about **17%** for the non-hard error rules (175 findings);
- 4.8% for the compile-break and wiring rules, which is measured, not
  estimated.

The 755 verdicts were judged by reading the code at each finding. The 313
compile-break and wiring findings were judged in this session. The 442
sampled findings were split over five parallel review passes with the same
instructions, then read through and spot-checked. A sample of 8 is small: 8
of 8 true still leaves a wide interval. Where fewer than 5 findings were
sampled, the table gives the count and no percentage.
